# Тестирование: Testcontainers, Locust и GitHub Actions

Unit-тесты проверяют бизнес-границы без БД, интеграционные тесты запускают настоящие PostgreSQL/Redis через Testcontainers. Locust создаёт нагрузку; GitHub Actions запускает тесты и go vet на push и pull_request.

```sh
./test.command
./start.command
./load.command
```

`./load.command` запускает два замера по 45 секунд: 50 и 200 пользователей. `./locust.command` открывает интерактивный Locust на http://127.0.0.1:8089. Он работает в терминале до Ctrl+C. Для нагрузки создаётся отдельный учебный аккаунт; его токен не записывается в отчёт или Git.

Нагрузка: 70% список меню, 20% карточка, 10% создание заказа, пауза 10–50 мс. Все виртуальные клиенты используют один тестовый счёт: это намеренная проверка конкуренции за одну строку баланса, а не модель независимых 200 покупателей. Показания pg_stat_activity записываются параллельно. Отчёты HTML/CSV и сырые результаты находятся в `evidence/`.

Красный CI виден, но серверный запрет слияния не включён. Поэтому пункт «красный CI автоматически блокирует merge» пока не закрыт. Draft PR не объединён.

**Бонусы Go:** реализованы собственный JSON contract-test и мутационный runner. Это не Pact и не mutmut: последний работает с Python и не мутирует Go. Не называй эти проверки запуском Pact/mutmut и не считай буквальные бонусы методички выполненными. Четыре пойманные мутации подтверждают только указанные четыре ошибки, а не отсутствие любых багов.

## Запуск на Mac

Открой терминал VS Code в `solution-go` этой работы:

```sh
./start.command
```

Перед переходом к другой работе выполни `./stop.command`. Порты общие, а базы, тома и проекты Compose раздельные. Остановка сохраняет данные. Первый запуск требует сети для скачивания образов; `.env` создаётся автоматически со случайными секретами. Настоящие секреты не включены в Git и архив.

Демонстрационные учётные записи: `student@example.com`, `student2@example.com`, `cook@example.com`, `courier@example.com`, `admin@example.com`. Пароль всех: `SiriusDemo2026!`. Это только локальные учебные аккаунты. Своего пользователя можно создать через `POST /users/register`.

## Как ориентироваться в проекте

| Путь | Что находится |
|---|---|
| `cmd/api/main.go` | Точка входа: конфигурация → PostgreSQL → миграции → HTTP-сервер |
| `internal/app/app.go` | Сборка зависимостей и регистрация всех HTTP-ручек |
| `internal/*/router.go` | Хэндлеры: читают запрос, вызывают сервис, формируют ответ |
| `internal/*/service.go` | Бизнес-правила: разрешено ли действие и как посчитать результат |
| `internal/*/repository.go` | SQL-запросы, транзакции и блокировки |
| `internal/auth/` | JWT, bcrypt, роли, проверка пользователя и Redis rate limit |
| `internal/domain/domain.go` | Общие модели и деньги в целых копейках |
| `internal/database/migrations/` | SQL-миграции, применяются при запуске; контроль checksum |
| `internal/config/config.go` | Чтение переменных окружения и локального `.env` |
| `internal/transport/http.go` | JSON, ошибки HTTP, ID из пути, пользователь в context |
| `cmd/seed/main.go` | Демонстрационные пользователи и меню; без сброса существующих данных |
| `docker-compose.yml` | Контейнеры, внутренние адреса, тома и зависимости запуска |
| `Dockerfile` | Сборка Go-бинарников в образ, запуск без Go-компилятора |
| `go.mod`, `go.sum` | Версии зависимостей и контроль целостности |
| `.env.example` | Образец настроек без настоящих секретов |
| `evidence/` | Сохранённые результаты реально выполненных проверок |
| `DEFENSE.md` | Короткий рассказ и вопросы для защиты |
| `REPORT.md` | Что проверено, результаты и ограничения |
| `FILEMAP.md` | Карта каждого исходного файла и основных функций |

В Go `func` объявляет функцию, `(s Service)` перед именем — метод типа Service, `ctx` переносит отмену/срок запроса и связанные значения. `defer` откладывает освобождение ресурса до выхода из функции. Возврат `(результат, error)` требует проверить ошибку до использования результата. Интерфейс задаёт нужные методы: сервису не требуется знать конкретный SQL-репозиторий.

После измерения `loadcleanup` останавливает worker/scheduler, убирает из очереди только фоновые задания своего load-аккаунта, помечает их cancelled и возвращает процессы. Заказы и результаты измерений сохраняются; остальные аккаунты и задачи не затрагиваются. Это не даёт тысячам учебных PDF/email/SMS обрабатываться часами после теста.

Проверенные замеры: 50 пользователей — 828.10 RPS, p95 74мс; 200 — 880.90 RPS, p95 310мс; HTTP-ошибок 0. Для POST /orders/create p95 вырос со 160 до 410мс. В выборках БД наблюдались блокировки tuple/transactionid и ожидания WALWrite/WALSync: узкое место этого сценария — транзакционная запись и конкуренция за горячий счёт.
