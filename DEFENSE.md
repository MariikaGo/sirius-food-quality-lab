# Защита: тесты и нагрузка

Скажи: «Unit-тесты изолируют бизнес-правила, интеграционные проверяют HTTP с настоящей PostgreSQL. Testcontainers создаёт пустые контейнеры на прогон, миграции создают схему, фикстуры — данные. Locust даёт нагрузку, CI повторяет тесты на GitHub».

Показ: `./test.command` → `testmain_test.go` → unit test → `./locust.command` и 50/200 пользователей → сохранённый load-summary/ожидания БД → Actions зелёный и draft PR красный. `./load.command` повторяет два измерения автоматически. Мутации: `python3 scripts/mutations.py`.

| Вопрос | Ответ |
|---|---|
| Пирамида тестов? | Много быстрых unit, меньше интеграционных, немного дорогих E2E. |
| Testcontainers — mock? | Нет, запускается реальный PostgreSQL в Docker, но с тестовыми данными. |
| Откуда схема? | Наши SQL-миграции, затем минимальные фикстуры. |
| Изоляция? | Новый контейнер на прогон, таблицы пересоздаются для каждого теста, параллельный запуск этих фикстур не используется. |
| Что видим в Locust? | RPS, latency p95, число/долю ошибок. Виртуальные пользователи не равны RPS. |
| Где узкое место? | Смотри REPORT и сырые ожидания pg_stat_activity: вывод относится к конкретному прогону, а не любому сценарию. |
| Почему общий счёт? | Контролируемо нагружаем блокировку одной строки баланса; это стресс горячего объекта. |
| Контракт? | Формат сообщения, ожидаемый consumer; несовместимое изменение должно провалить проверку до запуска. |
| Мутация? | Искусственно меняем условие и проверяем, поймает ли тест ошибку. Выжила — тесты это изменение пропустили. |
| Покрытие достаточно? | Нет: строка могла выполниться без проверки правильного результата. |
| CI? | Автоматический go test/go vet при push/PR. Требование merge gating отдельно настраивается в GitHub. |
| Блокировка merge? | На приватном репозитории текущий тариф отклонил защиту ветки; красный CI есть, запрета слияния пока нет. |
| Pact/mutmut? | У нас собственные проверки на Go, не эти инструменты. Их буквальные бонусы не заявляем. |
