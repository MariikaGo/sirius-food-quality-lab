# Шестая: рассказ по целям и понимание Go

## Рассказ на полминуты

«Я вынесла выполнение доставки в отдельный gRPC-сервис. Контракт описала в proto, из него сгенерированы сообщения и клиент/сервер. В HTTP API вместо локального сервиса передаю gRPC-клиент через интерфейс Gateway. Добавлены дедлайны и преобразование сетевых ошибок в HTTP-ответы. Остальные модули оставлены в монолите — это постепенное выделение Strangler Fig. Есть учебный поток статусов и двунаправленный чат с автоответом».

## Цель → реализация → что сказать

1. gRPC: бинарные сообщения Protobuf передаются по HTTP/2 между API и delivery. Успех HTTP-ручки назначения и лог отдельного контейнера доказывают сетевой вызов. Это не очередь Asynq из пятой.
2. Контракт: proto/delivery.proto. service задаёт методы; message задаёт поля; =1, =2 — номера полей в бинарном формате, не значения по умолчанию. Номера существующих полей нельзя произвольно менять/повторно использовать.
3. Отдельный сервис: cmd/delivery/main.go слушает TCP, регистрирует сервер и вызывает Serve. Бизнес-правила остаются в delivery/service.go, SQL в repository.go; теперь они вызываются процессом delivery.
4. Интеграция: app.go создаёт rpcClient и передаёт в delivery.Handler{Service: rpcClient}. Хэндлер знает интерфейс Gateway, а не детали сети. Назначение проходит router.Assign → client.Assign → Stub.AssignCourier → server.AssignCourier → Service.Assign → Repository → ответ обратно.
5. Strangler Fig: выделен только delivery; users/menu/orders ещё внутри API. База общая — промежуточный этап, не полная независимость данных.
6. Ошибки: client.ctx задаёт дедлайн; translate преобразует gRPC-ошибку в доменную; transport превращает её в HTTP. NotFound→404, PermissionDenied→403, Unavailable→503, DeadlineExceeded→504. Неизвестные коды текущий клиент тоже сводит к unavailable.
7. Server Streaming: один запрос TrackDelivery — несколько сообщений DeliveryStatus. В server.go stream.Send, в client.go stream.Recv до io.EOF. Статусы имитируются, база от потока не меняется.
8. Bidirectional Streaming: обе стороны могут отправлять сообщения. server.ChatWithCourier читает Recv и отвечает Send; наш клиент делает последовательные пары отправка/ответ. Реального чата двух людей нет, сервер отвечает автоматически.

## Один вызов Assign — разбор Go

Открыть internal/rpcdelivery/client.go, Assign.

`func (c *Client) Assign(...) (domain.Delivery, error)` — метод типа *Client, возвращает доставку и ошибку. c — экземпляр клиента, у него есть канал, Stub, токен и тайм-аут.

`actor *domain.User` — указатель на пользователя; nil означает отсутствие пользователя. Проверка nil нужна до обращения actor.ID.

`ctx, cancel := c.ctx(ctx, c.Timeout)` — подготовить контекст с внутренним ключом и дедлайном. Контекст передаёт отмену и срок выполнения, а не сами данные заказа.

`defer cancel()` — освободить ресурсы контекста при выходе, включая выход по ошибке. Не запускает goroutine и не ждёт тайм-аут.

`&pb.AssignCourierRequest{...}` — создать структуру запроса и получить указатель на неё. pb — короткое имя импортированного пакета сгенерированных сообщений.

`v, e := c.Stub.AssignCourier(...)` — настоящий сетевой RPC; два результата: указатель на ответ и ошибка. := объявляет переменные.

`if e != nil { return domain.Delivery{}, translate(e) }` — обработать ошибку; Delivery{} — нулевое значение структуры. Ошибки в Go обычно возвращают явно, это не исключение.

`return domain.Delivery{...}, nil` — преобразовать сетевой ответ в нашу модель; nil означает отсутствие ошибки.

## Интерфейс: главный вопрос по Go

Gateway объявлен в internal/delivery/service.go: Assign, Get, Complete. Тип *rpcdelivery.Client имеет методы с такими сигнатурами, поэтому удовлетворяет Gateway автоматически. В Go не нужно писать implements. Компилятор проверяет это при передаче rpcClient в поле Service типа Gateway. Вызов h.Service.Assign выбирает реализацию, которую передали при сборке приложения.

## Остальные вопросы по Go

- `*Client` — тип указателя, `&Client{...}` — адрес созданного значения. `*actor` в выражении — разыменование указателя.
- Указатель-получатель позволяет работать с экземпляром без копирования всей структуры. Значение Client и *Client имеют разные наборы методов; здесь передаём указатель.
- `[]*pb.DeliveryStatus` — срез указателей на сообщения; append добавляет элементы, for читает поток.
- `io.EOF` — штатный конец потока, не авария.
- `interface` описывает поведение; struct хранит данные. Client — структура, Gateway — интерфейс.
- `go srv.Serve(...)` в тестах запускает goroutine; в основной программе Serve блокирует основной поток до остановки сервера.
- Встраивание pb.UnimplementedDeliveryServiceServer даёт стандартные реализации неописанных методов и помогает совместимости с генерируемым интерфейсом.
- Пара `(значение, error)` позволяет отдельно проверить успех до использования результата.
- `context.WithTimeout` ограничивает ожидание; не делает операцию быстрее. 5 секунд для unary, 15 для Track, 30 для Chat.
- grpc.NewClient создаёт канал, но соединение ленивое. Успешное создание Client не доказывает доступность сервера; нужен RPC.
- Канал переиспользуется для запросов и закрывается Close, а не создаётся заново в каждом методе.

## Показ без поиска файлов

Заранее открыть proto/delivery.proto, app.go, rpcdelivery/client.go, rpcdelivery/server.go, delivery/service.go. README держать рядом как карту.

./start.command → ./demo.command → docker compose logs --tail 20 delivery. Видны назначение и завершение в отдельном сервисе. Не запускать demo дважды подряд: четыре входа при лимите пять в минуту.

Для отказа: войти студентом в Swagger, GET /delivery/orders/{номер из демо} работает. docker compose stop delivery → тот же GET возвращает 503 или 504, GET /menu/items продолжает отвечать. docker compose start delivery → повторный GET снова работает. Либо одной командой ./fault.command. Это проверка изоляции сбоя и восстановления соединения, а не автоматического резервного сервиса.

Тайм-аут отдельно покрывает TestRPCErrors: медленный тестовый сервер и короткий дедлайн; клиент использует поле Client.Timeout. Свежий Docker-запуск 19.11.2026: все 18 тестов прошли, включая TestRPCErrors; вывод в evidence/docker-tests.txt.
